# DOTA RUINER Modernization Design

**Date:** 2026-10-19  
**Status:** Proposed for implementation  
**Repository:** `morphlxngg/dota-ruiner`  

## 1. Purpose

DOTA RUINER analyzes a public Dota 2 match from its Match ID and explains, in plain language, which players had the strongest negative and positive measured impact. The release must turn the existing prototype into a trustworthy static-first application without hiding uncertainty or presenting synthetic match facts as real data.

Correctness, stability, and security take priority over feature count. Every requested feature remains in scope, but the application must withhold a conclusion when the available OpenDota data cannot support it.

## 2. Non-negotiable constraints

1. **Analytical integrity:** no fabricated match data, time series, player names, or probability-like confidence percentages. A real-match result uses only fields returned by OpenDota and deterministic derived metrics whose formula is documented.
2. **API security:** a private OpenDota API key is read only by the local Node server from `OPENDOTA_API_KEY`. It is never placed in browser code, browser storage, query strings generated by the client, or committed files. GitHub Pages remains a keyless static deployment and calls public OpenDota endpoints directly.
3. **Explainable scoring:** Ruin Score and Impact Score have explicit model versions, configuration, component-level explanations, data-coverage information, categorical conclusion quality, and deterministic tests.
4. **Minimal persistence:** browser history stores only the data needed to reopen or compare up to 15 analyses. Storage writes must handle quota and corruption safely. Demo data is bundled, immutable, and visibly marked as demonstration data everywhere it appears.
5. **Implementation quality:** preserve the project's recognizable Dota-match identity while providing responsive layouts, WCAG-oriented accessibility, output escaping, safe DOM construction, and cancellation/ordering for concurrent requests.

## 3. Product language and claim boundaries

The product may use its established playful “кто заруинил” voice, but every analytical screen must state that scores are heuristic measurements, not proof of intent, blame, griefing, or fault for a loss.

The interface distinguishes three kinds of values:

- **Observed:** copied from the OpenDota response, such as kills, deaths, `gold_t`, or wards placed.
- **Derived:** deterministic calculations over observed values, such as damage per minute or participation share.
- **Unavailable:** omitted from scoring and rendered as “Нет данных” / “No data,” never coerced to zero.

The application does not display a numeric “confidence” probability. Instead, it displays a categorical conclusion quality of `high`, `medium`, `low`, or `insufficient`, based on data coverage, role certainty, parsing state, and separation between the leading candidates. This label is explicitly described as data quality, not statistical probability.

## 5. Data flow

1. The user enters a Match ID or a supported OpenDota/Dotabuff URL.
2. The client validates the complete input and extracts exactly one 7–12 digit Match ID.
3. A request coordinator aborts the previous request and assigns a monotonically increasing request token.
4. On localhost, the browser calls `/api/matches/:id`; on GitHub Pages or another static host, it calls the public OpenDota API directly without a key.
5. The API adapter distinguishes timeout, rate limit, not found, unparsed/partial, invalid response, and network failure.
6. `normalizeMatch()` validates the response and preserves missing values as `null`.
7. Role inference and scoring operate on the normalized model.
8. The renderer updates the screen only if the response token is still current.
9. A compact analysis snapshot is saved to local history after a successful real analysis. Demo analyses are not inserted into real-match history.

An API error produces an actionable error state. It never starts the demo automatically and never assigns the requested Match ID to bundled demo data.

## 6. Normalized match model

The normalized representation includes:

- match identity, start time, duration, patch, game mode, lobby type, scores, winner, and parsed-data status;
- two teams containing any valid number of players, with a warning unless the standard 5v5 composition is present;
- observed player fields as finite numbers or `null`;
- `personaname` when OpenDota provides it, otherwise a localized anonymous-player label;
- `gold_t`, `xp_t`, and other time series only when they are valid finite-number arrays;
- hero metadata obtained from OpenDota constants with a bundled fallback for offline/demo use;
- warnings for partial parsing, missing teams, unusual player counts, unknown heroes, invalid fields, and unavailable analytical components.

Matches shorter than five minutes, with fewer than two usable players, with no separable teams, or with no usable scoring components return a controlled “insufficient data” result rather than a verdict. Matches with 9 or 11 players remain renderable when both teams and at least two candidates are valid, but carry a composition warning.

## 7. Role inference

The five supported positions are Safe Lane Core, Mid, Offlane, Soft Support, and Hard Support. Inference combines, in descending authority:

1. valid lane/role observations (`lane_role`, `lane`, `is_roaming`);
2. hero roles from current OpenDota constants;
3. item and support activity evidence when available;
4. team-relative last hits and GPM as fallback signals.

The result is `{ position, certainty, evidence }`, where certainty is `high`, `medium`, `low`, or `unknown`. It is not a percentage. Contradictory or weak signals produce `unknown`; the scorer then uses mode-wide conservative benchmarks instead of silently labeling a player as support.

Hero identity can adjust broad expectations only through documented configuration. No hero pick is itself a negative or positive scoring factor.

## 8. Scoring model

### 8.1 Shared rules

- Model versions are exported constants and included in every analysis snapshot, starting with `ruin-v2.0.0` and `impact-v2.0.0`.
- All thresholds and weights live in `src/data/scoring-config.js`.
- Every component returns `{ id, labelKey, observed, expected, points, maxPoints, available, evidence }`.
- `normalizeScore()` sums only available component weights and maps earned points onto 0–100.
- `null`, `undefined`, non-finite values, and structurally invalid arrays mark a metric unavailable; they never become zero.
- Abandon and leaver status collapse into one `abandon` flag and cannot be double-counted.
- Turbo uses a dedicated benchmark profile. Ranked and standard public matches use the standard profile. Unsupported/custom modes use conservative generic benchmarks and display a warning.
- Raw score ties remain ties. UI ordering uses stable player-slot ordering and does not invent fractional differences.

### 8.2 Ruin Score v2

Target component weights:

| Component | Weight | Evidence |
| --- | ---: | --- |
| Deaths and survival errors | 25 | deaths per minute, team-relative deaths, available late-death timestamps |
| Role-relative economy | 20 | GPM, last hits per minute, net-worth rank, duration and mode profile |
| Damage efficiency | 20 | hero damage per minute, role expectation, damage relative to farm |
| Team participation | 15 | `(kills + assists) / team kills`, unavailable when team kills are zero |
| Objectives and role duties | 10 | tower damage plus observed warding, stacking, healing, or disable data appropriate to role |
| Macro efficiency | 10 | observed buybacks, late deaths, and advantage-loss evidence when real time-series data supports it |

Abandon/confirmed AFK is a visible verdict flag and a configured bounded component; it never creates a score above 100 and never duplicates another source field. “Throw” language is used only when a real team-advantage time series and a temporally associated observed event support it. Otherwise the component is unavailable.

### 8.3 Impact Score v2

Impact is not `100 - Ruin Score`. Its target weights are:

| Component | Weight | Evidence |
| --- | ---: | --- |
| Teamfight participation | 25 | kills, assists, team kills |
| Hero contribution | 25 | role-adjusted damage, disables, healing and saves when observed |
| Economy efficiency | 15 | GPM/net worth relative to position and match duration |
| Objectives | 15 | tower and objective contribution when observed |
| Role contribution | 10 | warding, stacking, healing, or core pressure according to inferred role |
| Survival | 10 | deaths per minute and team-relative survival |

### 8.4 Coverage and conclusion quality

`dataCoverage` is the ratio of available configured component weight to total configured component weight. It may be displayed as a coverage percentage because it is an exact statement about fields used, not a probability.

- Under 50% coverage: no primary ruiner/carry verdict; show “insufficient data.”
- 50–69%: low conclusion quality.
- 70–84%: medium conclusion quality.
- 85–100%: potentially high, subject to role certainty and candidate separation.

Candidate separation modifies only the categorical quality label. It never becomes a probability. When the two leading scores are too close under configured deterministic thresholds, the UI says the result is ambiguous and presents co-leaders rather than overstating a winner.

## 9. Real charts

The chart offers Gold, XP, and Hero Damage tabs only when corresponding real series exist.

- Gold uses each player's `gold_t` values.
- XP uses each player's `xp_t` values.
- Hero Damage uses a time series only if OpenDota returns a compatible observed series; otherwise the tab is disabled with an explanation. Final hero damage is shown in player summaries but never expanded into a synthetic timeline.
- Series with different lengths are clipped to their shared valid range; gaps remain gaps and are not interpolated.
- Ruin and impact leaders receive distinctive stroke patterns as well as color, so meaning does not rely on color alone.
- Keyboard-accessible controls and a tabular summary provide a non-canvas alternative. Pointer/focus tooltips report minute, hero, and observed value.
- Resize uses `ResizeObserver`, and long hero names are handled in an external legend rather than painted over the plot.

If no valid time series exists, the chart panel shows final observed values and a clear “timeline unavailable” message.

## 10. User-facing features

### 10.1 History

`localStorage` keeps at most 15 versioned snapshots under one namespaced key. A snapshot contains Match ID, timestamp, mode, duration, model versions, data coverage, player display names and hero IDs, component results, final scores, warnings, and only the downsampled time series needed to reopen the chart. Raw API responses and API keys are never stored.

Before writing, the history module estimates serialized size, evicts oldest entries, and handles quota/security exceptions without breaking the current analysis. Invalid or older incompatible records are ignored or migrated by schema version.

### 10.2 Comparison

The user can compare the current match with the immediately previous stored match or select any two stored matches. Side-by-side comparison includes mode, duration, coverage, model version, leaders, team totals, and normalized player metrics. Scores produced by different major model versions are visibly marked non-comparable rather than directly ranked.

### 10.3 Player names

The app uses `personaname` returned with match data. If a name is unavailable, it displays “Игрок N” / “Player N.” It does not make extra account-profile requests merely to deanonymize players. Names are rendered with `textContent`, not HTML.

### 10.4 Share image

A canvas export creates a PNG containing the Match ID or “DEMO,” model version, data coverage, leaders, scores, key observed/derived factors, and the heuristic disclaimer. User-controlled text is drawn as text and length-limited. Web Share is used when available; download is the fallback.

Open Graph metadata uses a static branded preview because GitHub Pages cannot generate per-match server metadata.

### 10.5 Localization

RU and EN strings live in a key-based catalog. Russian is the default, and the user's selection is stored. Dynamic values use `Intl.NumberFormat` and `Intl.DateTimeFormat`. Domain modules return stable keys/evidence rather than localized sentences.

### 10.6 PWA

The manifest supplies install metadata and purpose-built icons. The service worker precaches the application shell and bundled demo data, and uses stale-while-revalidate for same-origin static assets. It does not claim that arbitrary OpenDota matches are available offline.

The latest successfully saved analysis can be reopened from local history offline. The demo is started only by its dedicated action and every demo screen/export displays a persistent “ДЕМО / DEMO — данные вымышлены” label.

## 11. UI and visual system

The recognizable dark Dota-match presentation remains, with a more evidence-led hierarchy.

- `arena` `#080A0F`: page background;
- `slate` `#151923`: panels;
- `ink` `#F4F6FF`: primary text;
- `risk` `#FF4D57`: negative measured contribution;
- `impact` `#42D7A1`: positive measured contribution;
- `uncertain` `#E9B949`: incomplete or ambiguous evidence.

Manrope remains the interface typeface; JetBrains Mono is limited to IDs and numeric measurements. The memorable element is the verdict/evidence area, which pairs each claim with its coverage and observed basis. Supporting panels are quieter and avoid repeated decorative card treatments.

Desktop layout:

```text
[brand] [history] [language]
[ Match ID                                      ][Analyze]
[request status / parsing and coverage warnings]
[negative-impact evidence] [positive-impact evidence]
[Gold | XP | Damage real timeline + accessible table]
[Radiant players]            [Dire players]
[comparison] [export]
```

On mobile, verdict sections become a single reading column, tables scroll within labeled regions, chart controls remain 44 px high, and primary actions stay visible without covering focused content.

## 12. Accessibility and safe rendering

- Semantic header, main, sections, headings, form labels, buttons, lists, and tables.
- Skip link, visible high-contrast `:focus-visible`, logical focus order, and no keyboard traps.
- Status and error regions use appropriate `aria-live`; loading sets `aria-busy` and provides a skeleton that is hidden from assistive technology.
- Color is supplemented by labels, icons, and chart stroke patterns.
- Interactive targets are at least 44×44 CSS pixels.
- Motion respects `prefers-reduced-motion`.
- Layout remains usable at 200% zoom and narrow mobile widths.
- User/API strings enter the DOM through `textContent`, attribute setters with allowlisted URLs, or a small element-construction helper. Raw API strings are never passed to `innerHTML`.
- Hero image URLs must match allowlisted Steam/OpenDota HTTPS origins; unknown URLs fall back to a local neutral asset.

## 13. Local server and API boundary

The ESM Node server listens on `127.0.0.1` by default and supports only `GET`, `HEAD`, and local preflight where needed.

### API route

`GET /api/matches/:matchId` validates the entire path segment with `^\d{7,12}$`. The upstream URL contains only the validated ID. If `OPENDOTA_API_KEY` is configured, it is sent in the upstream `Authorization: Bearer` header when supported by the configured OpenDota deployment; it is not accepted from the browser. If the upstream requires a query-key integration, that URL is created exclusively server-side and is redacted from all logs and error payloads.

The server accepts requests only from same-origin or allowlisted localhost origins. Production GitHub Pages cannot use this server; the README explains the resulting public API rate limits and the option to run locally with a server-held key.

### Reliability controls

- in-memory successful-response cache with a 10-minute TTL and bounded entry count;
- per-client token-bucket limit and a bounded upstream queue;
- request coalescing for concurrent requests for the same Match ID;
- upstream timeout and response-size limit;
- structured logs with request ID, route, status, duration, and cache outcome, excluding secrets and response bodies;
- graceful shutdown on `SIGINT`/`SIGTERM`, stopping new requests and waiting briefly for active requests;
- JSON security headers and `Cache-Control` appropriate to API responses.

### Static files

Development static serving uses the Vite development server. Preview/production-like serving exposes only Vite's `dist` directory, resolves paths below that root, uses asynchronous I/O, and never serves dotfiles, source files, `.env`, `.git`, tests, or arbitrary repository paths.

## 14. Loading, empty, and error states

- Initial state explains how to enter a Match ID and offers an explicitly labeled demo.
- Loading uses a skeleton, disables duplicate submission, and remains cancellable by a newer request.
- Errors distinguish invalid input, match not found, rate limiting, network failure, timeout, partial/unparsed data, and local-server configuration.
- Empty chart/history/comparison states explain the next available action.
- An older request can never overwrite a newer result, status, history entry, or URL hash.

## 15. Testing strategy

### Unit and integration tests

Vitest covers:

- deterministic scoring and 0–100 normalization;
- missing/null values excluded rather than treated as zero;
- zero team kills excluding participation;
- one abandon flag without double penalty;
- standard and Turbo benchmark selection;
- five-position inference and explicit unknown roles;
- coverage and categorical conclusion quality;
- normalized handling of 9/10/11-player and malformed matches;
- unknown heroes and unsafe player names;
- chart series selection with no synthetic fallback;
- history quota, corruption, eviction, and schema migration;
- request cancellation and last-request-wins behavior;
- server Match ID validation, cache, rate limit, method handling, CORS, and static path confinement.

Golden fixtures include parsed Ranked, Turbo, partial/unparsed, zero-kill, abandon, short, unusual-player-count, and demo matches. Fixture provenance and redaction are documented.

### Browser tests

Playwright verifies:

- real-match API failure never renders demo data;
- demo remains clearly labeled through analysis and PNG export;
- history reopen and two-match comparison;
- language switching;
- keyboard-only main flow;
- mobile verdict and chart layout;
- concurrent searches show only the latest result;
- offline shell, demo, and latest saved analysis;
- no untrusted player name is interpreted as markup.

Automated accessibility checks use axe in Playwright, supplemented by documented manual keyboard, 200% zoom, reduced-motion, and screen-reader smoke checks.

## 16. Build, CI, and deployment

`package.json` pins the supported Node version and provides `dev`, `start`, `build`, `preview`, `test`, `test:watch`, `test:e2e`, and `check` scripts. The lockfile is committed.

GitHub Actions runs install, unit tests, build, and browser smoke tests on pushes and pull requests. A separate Pages workflow deploys `dist` with the correct repository base path. `.nojekyll` is retained in the published artifact.

The service worker version derives from the build and removes obsolete caches on activation.

## 18. Delivery stages

1. **Integrity foundation:** project tooling, normalized model, request errors/cancellation, real-only charts, scoring v2, and core tests.
2. **Modular interface:** split render/state/chart modules, accessible responsive redesign, localization, constants synchronization, and player names.
3. **Persistence and sharing:** bounded history, comparisons, PNG export, and static Open Graph assets.
4. **PWA:** manifest, icons, service worker, offline demo, and last-analysis behavior.
5. **Secure local service:** cache, limiter, queue, server-held key, safe static serving, logging, and shutdown.
6. **Release hardening:** full browser coverage, accessibility checks, CI/Pages workflows, screenshots, README, CONTRIBUTING, and license.

Each stage must leave the application runnable and its tests green. Integrity-stage behavior cannot be weakened to complete a later feature.

## 19. Acceptance criteria

The release is complete when:

1. A failed OpenDota request never renders demo data or labels demo data with the requested Match ID.
2. Every chart point comes from a validated OpenDota time-series value; missing history produces no synthetic line.
3. Every calculated score is deterministic, versioned, explainable, normalized to 0–100, and covered by tests.
4. Missing fields are excluded and identified; zero team kills do not create a participation penalty.
5. Leaver/abandon evidence cannot be double-counted.
6. Standard, Ranked, Turbo, custom, partial, and unusual-player-count matches receive controlled profiles or warnings.
7. Role uncertainty and data coverage are visible, and insufficient data suppresses the main verdict.
8. No UI element describes conclusion quality as a probability.
9. Two rapid requests can update the UI, URL, and history only from the latest request.
10. Unknown heroes, anonymous players, hostile player names, and unavailable portraits do not break or inject markup into the interface.
11. History is bounded to 15 compact entries and survives corrupt or quota-limited storage.
12. Comparison, RU/EN, PNG export, skeleton loading, mobile layouts, and real chart tooltips work in browser tests.
13. The installable PWA works offline for its shell, explicitly labeled demo, and latest saved analysis without claiming live API access.
14. The local server does not expose `.env`, `.git`, source files, or traversal paths; it rate-limits, caches, queues, logs safely, and shuts down gracefully.
15. No browser bundle, stored value, client request, log entry, or committed file contains the private API key.
16. GitHub Pages builds and deploys the static application without Node runtime assumptions.
17. Keyboard navigation, focus visibility, live status announcements, contrast, reduced motion, and 200% zoom pass the documented checks.
18. CI passes unit tests, browser smoke tests, and the production build.

## 20. Explicit non-goals

- No account system, cloud database, or cross-device history.
- No LLM-generated coaching or unsupported claims about player intent.
- No promise of per-match dynamic Open Graph images on GitHub Pages.
- No attempt to reconstruct missing timelines from final totals.
- No claim that heuristic scores are validated statistical measures until a separately documented benchmark study exists.
